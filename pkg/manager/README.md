# pkg/manager

## Intention

`pkg/manager` is the controller-runtime integration layer for the platform's reconciler/provisioner model. It is the package that turns the lower-level provisioner contract into an operational controller process with shared startup, reconcile, teardown, status, and deletion-ordering behavior.

This package is where several lower-level ideas become enforceable runtime policy:

- the reconciler-oriented provisioner contract from [pkg/provisioners](../provisioners/README.md)
- the "yield instead of block" progress model driven by `provisioners.ErrYield`
- the context-scoping and client-access model described in [pkg/client](../client/README.md)
- the shared runtime/bootstrap options from [pkg/options](../options/README.md)
- the controller-specific option layer in [options](./options/README.md)

In practice `pkg/manager` does three jobs:

- bootstraps controller processes through `RunService(service, f)`, or the deprecated `Run(f)`
- implements the generic reconcile loop through `Reconciler`
- manages cross-resource deletion ordering through resource-reference helper functions

## Invariants And Guard Rails

- `ControllerFactory` is the top-level integration contract for controller binaries built on this package.
- `Run()` and `RunService()` are framework bootstrap code, not generic library helpers. They own flag wiring, logging, OpenTelemetry setup, optional upgrade/initialize hooks, manager creation, controller creation, watch registration, and process startup.
- `Run()` is deprecated: it pushes metrics through the deprecated `SetupOpenTelemetry()`. `RunService()` calls `SetupTracing()` and `SetupMetrics()` with its service name instead, so metrics are only scraped from the manager's metrics endpoint.
- `Reconciler` is the shared reconcile-policy implementation for manager-style resources. It injects the shared execution context that descendant provisioners depend on before invoking them.
- That injected context includes:
  - manager access via `pkg/manager`
  - namespace and static Kubernetes client via [pkg/client](../client/README.md)
  - active cluster scope via `client.ClusterContext`
  - CD driver context
  - managed-resource context for [pkg/provisioners/application](../provisioners/application/README.md)
- `provisioners.ErrYield` is a first-class control signal here. It means "stop now and requeue on the fixed yield timeout" rather than "return a hard reconcile error."
- During normal reconcile, even unexpected provisioner errors are intentionally translated into status updates plus a fixed requeue (or the poll slot, under `WithPolling()`), rather than returned as raw reconcile errors, to avoid controller-runtime exponential backoff harming throughput.
- Info means handled, error means a surprise. A provisioning failure that carries a disposition (`Yield()`, `Recheck()`, `Terminal()`, `UserActionRequired()`, or one of their sentinels wrapped) was handled by the provisioner and is logged at info; a plain yield is not logged. A failure without a disposition is a bug or a fault nobody planned for, and is logged at error on every pass. A polling controller repeats a handled failure every period, so logging it at error level would page someone once a minute per resource.
- Terminal dispositions (`provisioners.ErrTerminal`, `provisioners.ErrUserActionRequired`, tested via `provisioners.IsTerminal`) are the exception to the requeue-everything rule **on the provision path of a controller without `WithPolling()` only**: the condition is written, but the resource is **parked** — no requeue — because retrying a non-self-healing failure only burns the workqueue. Revival is out-of-band: a spec change (generation bump) wakes an `ErrUserActionRequired` resource through the consumer's watch predicate, while `ErrTerminal` awaits operator intervention. The terminal-vs-retrying distinction lives in the requeue decision, not the surfaced condition: both write `ConditionFalse`. The condition `Reason` defaults to `Errored`, but a typed `provisioners.Error` overrides it with its own reason (see below), so e.g. a terminal `DependencyNotFound` surfaces as such.
- A successful provision **parks by default** — no requeue — because a level-triggered resource is woken by a watch when its spec changes. A controller whose resources are backed by an external system that moves on its own gets no such watch event, so it opts into polling by passing `WithPolling()` to `NewReconciler`; that makes a successful reconcile requeue at the resource's next slot in `options.RequeuePeriod` instead. Polling is a code-level property of the controller, not a flag, because whether re-observation is needed follows from what backs the resource; a non-positive `RequeuePeriod` therefore falls back to `constants.DefaultRequeuePeriod` rather than silently parking, since controller-runtime treats a non-positive `RequeueAfter` as "done". The alternative to polling in the reconcile pass — a second process that polls and patches status — is a split brain, and is what this option exists to make unnecessary: two writers means neither owns the conditions, transitions authored by one are invisible to the other's before/after diff, and their writes churn or conflict on optimistic locks.
- **A poll always requeues at `handler.LowPriority`**, the priority controller-runtime gives the start-up list. A requeue otherwise keeps the priority of the pass it came from, so a resource once woken by a watch event would poll at normal priority for ever after, and on a large fleet the polls would compete with new work. Yields set no priority, so a yield inherits the priority of the pass it came from: a poll that finds drift and yields stays at `LowPriority` while it repairs, behind all normal-priority work, until a watch event lifts it. That is deliberate: a repair the controller found for itself should not jump work a user is waiting on. The same inheritance has a cost after a restart: everything comes in from the start-up list at `LowPriority`, so a user's create that was mid-provision when the process restarted keeps yielding in the low lane, first come first served behind the fleet's polls, until a watch event lifts it. Status writes do not lift it where the watch filters on generation. That only bites if the worker pool cannot keep up with the polls; a pool that keeps up drains the low lane every period. This needs the priority queue, which is controller-runtime's default.
- **A poll requeues through `nextSlot`.** Each resource's UID hashes to a fixed offset within the period, and a poll waits until that resource's next slot. controller-runtime schedules a requeue for exactly the duration given, so without this, resources that finish together stay together: the initial informer list drains the whole fleet into a narrow window, every resource re-arms exactly one period after its own completion, and that window only drifts apart as fast as pass times vary, which for similar resources is very slowly. Slotting by UID spreads the fleet across the whole period in one cycle. Every restart or leader change still starts with the initial list as one worker-bound burst, but because the slot comes from the UID and the wall clock, not from when a pass finished, the fleet re-spreads within a period and a tenth of the end of that burst. A random delay per pass (`wait.Jitter`) does not give the same thing: a narrow jitter only drifts the fleet apart over tens of passes, and one wide enough to spread it in a single pass means the gap between passes is no longer the period. Slotting gets both: the fleet spreads in one cycle, and in steady state passes start exactly a period apart.
- The wait is never zero, which would park a polling controller, and never less than a tenth of the period, except where skipping a slot would overflow, which needs a period of about 265 years. In steady state a pass runs at its slot and the next one is exactly a period later. After an out-of-band wake (a spec edit, a yield, a restart) the next pass snaps to the slot, so that one gap can be shorter than a period; the period is the spacing of slots, not a minimum gap between passes. A slot less than a tenth of the period away is skipped for the one after it, so a pass that ends just before its slot is not requeued to run again straight away and hit the provider twice back to back. A watch event during a pass still wakes the resource at once, as it always has; the gap only governs the requeue.
- **A polling controller never parks, and only a plain yield is retried sooner.** Every other outcome of a pass — success, `Recheck()`, `Terminal()`, `UserActionRequired()`, an unexpected error, and a failed status write — requeues at the resource's next slot, at `LowPriority`. Nothing watches the external system, so a parked resource would never be looked at again however the fault cleared; and a fault that is not moving gains nothing from a pass every ten seconds, while a fleet hit by one fault at once would hammer a provider that is already unwell. A failed status write is slotted too, so a struggling API server is not retried six times as hard by every polling resource. Under polling, `Terminal()` and `UserActionRequired()` therefore only set the condition: a step that costs money or destroys data must check its own facts before acting again, because the next pass will run it.
- **Yields are not slotted.** A plain yield, and for a controller without `WithPolling()` also unexpected provisioner errors and failed status writes, requeue a flat `constants.DefaultYieldTimeout` after the pass ends; failed finalizer removals do for every controller. They are deliberately left flat: slotting them would start passes 10s apart instead of resting 10s after each one, so the slower the pass the shorter the rest, and a slow, failing provider would be retried harder just when it should be eased off. It would also use up attempt-counting retry caps sooner. The cost of keeping them flat is that a bunch of retries, from a restart or one watch event waking many resources, stays bunched on the retry path; pass times vary enough to drift it apart.
- One cost of polling remains, and it is not a regression against running a separate polling process: `handleReconcileCondition` writes status on every pass, so a polling controller makes one write request per resource per period. The API server short-circuits a semantically identical write, so there is no etcd write, no `resourceVersion` bump and no watch storm — but the request itself is newly constant rather than rare. Gating that write on the existing `changed` flag would **not** be a safe fix: `changed` is computed from the `Available` condition alone and would drop any other status field a provisioner mutated in memory.
- Size a polling controller before turning it on. Each pass runs the whole provisioner, writes status and logs twice, and controller-runtime sets no client-side rate limit (QPS is -1), so nothing but the worker pool slows it down. 20k resources on the one-minute default is about 333 passes a second, which a small pod (100m CPU) is unlikely to sustain; if the pool cannot keep up, the fleet is simply observed less often than the period says. Pick the period from the measured cost of a pass against the provider rather than taking the one-minute default: there is one flat period, with no slower cadence for resources that have settled, and no coalescing of provider reads across resources.
- **`WithTransient()` keeps an outage off the condition.** A provision that failed because it could not reach a service has learned nothing about the resource, so with `WithTransient()` it leaves the `Available` condition as it was, still saves the rest of status, and is logged at info. Without it an outage flips every resource to `Errored` and back, and each flip is a transition on the provisioning stream. Core classifies network errors, timeouts (a context deadline is a `net.Error`, so a step's own timeout counts) and the Kubernetes errors that mean "could not reach" (server timeout, timeout, too many requests, service unavailable); an internal error or a conflict is an answer, not an outage, and a cancelled call is shutdown, though the client wraps it in a network error. The consumer passes classifiers for the external systems it owns, and should treat a plain 500 from them the same way, as an answer: one that keeps coming back would otherwise show progress for ever. A failure with a disposition (`Yield()`, `Recheck()`, `Terminal()`, `UserActionRequired()`, or a sentinel wrapped) is never transient, because the provisioner chose what to report: hiding a wrapped `ErrTerminal` would leave a parked resource reading `Provisioned` for ever. An unreached service is logged at info. `Unreachable()` exports the same test, so a provisioner that keeps its own status in step with the condition (an attachment row, say) agrees with it. The delete path ignores the classifier: a stale `Provisioned` would tell `ResourceReady` a dying resource is ready. The cadence is unchanged: an unreached service waits for the next slot, like any other failure.
- **Yield only for work that is moving.** A yield says something will finish by itself soon: an action the external system accepted and is still doing, or a dependency that is still provisioning. A wait on something that is not moving but may recover — a failed dependency (`DependencyFailed`), an external resource in an error state — is a `Recheck()`: a polling controller waits for the next slot, and everything else treats it as the yield it wraps. A request the external system rejected is never a yield; repeating it every ten seconds only repeats the rejection. A recheck always goes to the low lane, even from a normal-priority pass such as a user's spec edit: the fault is not the controller's to clear, and the user's next edit wakes it at normal priority anyway. A recheck from one child of the concurrent combinator can hide what a sibling returned, because the group keeps only the first error: a sibling's yield then waits for the slot. Return a recheck only from a provisioner that owns the whole decision.
- A paused resource stops being polled, because the pause check returns before `reconcileNormal`. That is intended — pause means stop — but it does mean "parked" and "silently stale" look identical for a polling controller, so a consumer must ensure unpausing actually generates an event. Expressing pause as a spec field does this for free through a generation-change predicate; expressing it as an annotation would not.
- The delete path does **not** honour terminal dispositions: a `Deprovision` that returns a terminal error is treated as an ordinary hard error (returned to controller-runtime, exponential backoff), because parking a deletion would strand the finalizer and leak the resource. Do not return `Terminal()`/`UserActionRequired()` from `Deprovision` expecting it to park — yield and keep converging instead.
- The `Available` condition is written reason-native: `handleReconcileCondition` seeds a lifecycle default (`Provisioning`/`Deprovisioning`/`Errored` plus a matching message), then, if the error is a typed `provisioners.Error`, overrides `Reason` with its `Reason()` and `Message` with its `Message()` via `SetProvisioningCondition` — no flattening into one string. Operator-only detail is kept off the condition by living in the error's `fmt.Errorf` wrapping instead, which `errors.As` sees past to recover only the safe surface (CWE-209). Bare (untyped) errors keep the lifecycle default — a lifecycle word on the yield path, or a fixed, generic `an unexpected error occurred` on the errored default path. The untyped error is **never** stringified onto the condition: the condition is user-visible — it is projected onto the API `provisioningStatusDetail` **and** emitted verbatim on the `provisioning` log stream — so surfacing raw error text there would leak internal detail (CWE-209, fail-closed). The raw error is logged operator-side by `reconcileNormal` instead. New failure modes should still return a typed `provisioners.Error` so the user gets a *specific* safe reason/message rather than the generic fallback. It also means a typed yield (e.g. `DependencyNotReady(...)`) surfaces its reason and detail on the `Available` condition instead of a bare `Provisioning`. (Condition messages are lowercase with no trailing punctuation, matching the Go error-string convention.)
- The typed-error override enriches reason/message on every path but is **assumed failure-side**: the `Dependency*` constructors are provision-side, so on the deprovision path the override is currently inert. If a `Deprovision` ever returns a typed error, its failure reason replaces the `Deprovisioning` lifecycle reason on the raw condition. That is deliberate rather than guarded against: the coarse API status keys off the deletion timestamp (not the reason) and the requeue decision keys off the disposition, so surfacing the blocker in `Reason` is informative, not misleading. Revisit — with a test — only when a deprovision-side typed error actually exists.
- During delete reconcile, synthetic resource references and owned-resource finalizers are checked before child deprovisioning is allowed to proceed.
- The resource-reference helpers implement the platform's deletion-ordering contract by encoding references as extra finalizers on referenced resources.
- `ResourceReady()` is the shared readiness gate for dependent resources and returns `provisioners.ErrYield` when a dependency is not yet provisioned.

## Lower Layers

- [options](./options/README.md): controller-specific options built on [pkg/options](../options/README.md), including max concurrency, the polling requeue period, and CD driver selection.
- [provisioners](../provisioners/README.md): the child lifecycle contract that this package drives.
- [client](../client/README.md): namespace/client/cluster context propagation used by the reconciler.
- [provisioners/application](../provisioners/application/README.md): receives the managed-resource and CD contexts injected here.

## Caveats

- The package boundary is broad. It mixes process bootstrap, reconcile policy, context propagation, readiness helpers, and deletion/reference semantics.
- `pkg/manager` is tightly coupled to the in-tree CD model. `getDriver()` currently hardcodes ArgoCD driver selection and treats anything else as unsupported.
- The shared reconcile loop relies on substantial hidden context setup before provisioners run. That is efficient for repository consistency, but it means many downstream components depend on implicit prerequisites rather than explicit method arguments.
- The deletion-ordering model is powerful but also compromised: resource references are encoded as finalizers, and `GenerateResourceReference()` still carries legacy naming baggage including the `unikorn-cloud.org` to `kubernetes.unikorn-cloud.org` group rewrite.
- `Run()` exits the process directly on setup failures. That is appropriate for controller binaries, but it reinforces that this package is an operational framework layer rather than a clean reusable library.
